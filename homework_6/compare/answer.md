## Объяснение решения

mergesort делит массив пополам, рекурсивно сортирует каждую половину и сливает результаты;

в merge сравниваем первые еще не взятые элементы двух списков и добавляем меньший. когда один список закончился, дописываем остаток другого. поэтому после слияния получаем отсортированный список со всеми исходными элементами;

базовый случай - массив длины 0 или 1, он уже отсортирован. значит, по индукции правильно сортируются и все более длинные массивы;

quicksort выбирает последний элемент опорным. partition переносит элементы <= pivot в начало участка, а затем ставит pivot сразу после них. слева от него значения не больше, справа - больше. сам опорный элемент уже находится на окончательной позиции;

остается отсортировать обе части. меньшую обрабатываем рекурсивно, большую - циклом в текущем вызове. это замена хвостовой рекурсии: разбиения остаются теми же, но на упорядоченном массиве не получаем стек глубины n;

когда в участке меньше двух элементов, сортировать нечего. после обработки обеих частей весь участок отсортирован;

обе функции возвращают новый список и не меняют исходный;

timer запоминает perf_counter перед вызовом функции и после него, печатает разницу в секундах и возвращает результат. *args и **kwargs передают аргументы, wraps сохраняет имя и описание функции;

декоратор применяем к внешним вызовам в блоке __main__, поэтому замеряем всю сортировку целиком, без печати на каждом рекурсивном шаге. если функция выбросит исключение, оно передается вызывающему коду, время такого вызова не печатается.

## Оценка сложности

пусть n - длина массива, сравнение и обмен чисел занимают O(1);

mergesort: O(n log n) времени во всех случаях. на каждом уровне деления суммарно сливаем n элементов, уровней O(log n). дополнительная память O(n) на срезы и слияния, стек O(log n); одновременно хранящиеся массивы вдоль одной ветви имеют суммарную длину O(n);

quicksort: в среднем O(n log n) времени для случайного порядка различных чисел. в худшем случае O(n²): опорный каждый раз оказывается крайним, получаем n + (n - 1) + ... + 1 операций. так происходит на возрастающем, убывающем массиве и на одинаковых значениях при выбранном partition;

стек quicksort занимает O(log n) даже в худшем случае, тк рекурсивно идем только в меньшую часть, длина которой не больше половины текущего участка. копия исходного массива занимает O(n), итого дополнительная память O(n);

timer добавляет O(1) времени и памяти на внешний вызов, если считать длину имени функции постоянной. время самой функции в эти дополнительные затраты не входит;

для пустого массива и одного элемента обе сортировки работают за O(1).

## Визуализация

mergesort для [5, 2, 8, 1, 3]:

```text
[5, 2, 8, 1, 3]
├── [5, 2]
│   ├── [5]
│   └── [2]
│   слияние -> [2, 5]
└── [8, 1, 3]
    ├── [8]
    └── [1, 3]
        ├── [1]
        └── [3]
        слияние -> [1, 3]
    слияние -> [1, 3, 8]

[2, 5] + [1, 3, 8] -> [1, 2, 3, 5, 8]
```

в последнем слиянии последовательно берем 1, 2, 3, 5, затем дописываем 8;

quicksort на том же массиве, индексы включительно:

| Участок | Опорный | Массив после partition | Позиция опорного |
| --- | --- | --- | --- |
| 0..4 | 3 | [2, 1, 3, 5, 8] | 2 |
| 3..4 | 8 | [2, 1, 3, 5, 8] | 4 |
| 0..1 | 1 | [1, 2, 3, 5, 8] | 0 |

в первом разбиении сначала переносим 2 в начало, затем 1 на следующую позицию и меняем 3 с 8. получаем две части длины 2;

при равных длинах реализация сначала рекурсивно обрабатывает правую часть [5, 8], затем циклом левую [2, 1]. участки длины 0 и 1 сразу заканчиваются.

## Сравнение времени

запуск из корня репозитория:

```bash
python3 homework_6/compare/algo.py
```

для каждого массива делаем три замера каждой сортировки. данные создаем до запуска таймера, обеим функциям передаем один и тот же исходный массив. генератор случайных данных имеет seed = 42;

результаты одного запуска для n = 3000, в таблице медиана трех замеров в секундах:

| Массив | mergesort | quicksort |
| --- | --- | --- |
| случайный | 0.004269 | 0.002458 |
| возрастающий | 0.002808 | 0.261630 |
| убывающий | 0.002801 | 0.190170 |
| одинаковые числа | 0.002615 | 0.257987 |

на случайном массиве quicksort немного быстрее. на остальных массивах разница примерно в 70–100 раз в пользу mergesort: quicksort делит участок на пустую часть и часть длины на 1 меньше;

точное время зависит от компьютера и нагрузки. такое поведение относится к этой реализации quicksort с последним опорным и разбиением на две части. случайный опорный помогает на упорядоченных данных, а разбиение на три части - при большом числе повторов.
